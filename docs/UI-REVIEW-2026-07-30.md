# Snoomp frontend review — UI, React, accessibility

**Scope:** `frontend/index.html`, `frontend/src/**` (6,018 lines across App.tsx, 6 components, dashboard.css)
**Date:** 2026-07-30 · **Version:** v0.2.1 · **Rev 3** — re-audited against v0.2.1; added the verification pass below and Part 6 (aesthetic assessment, dark and light)
*Rev 2 added Part 4 (design system) and Part 5 (menu reachability) against v0.2.0.*
**Method:** source audit against the Vercel Web Interface Guidelines, the Vercel React performance rules, and WCAG 2.2 A/AA. No dev server was running, so this is a static audit — live-DOM checks (computed contrast on real backgrounds, focus order, screen-reader announcement) are flagged for manual verification. Contrast ratios and CIELAB ΔE figures are computed from the CSS tokens and are exact.

---

## Headline

Five findings dominate everything else.

1. **There are zero `aria-*` attributes, zero `role=` attributes, and zero keyboard handlers in the entire frontend.** Every primary interaction — selecting a monitor, toggling theme, filtering by tag, expanding a group, opening the profile menu — is a `<div>` or `<span>` with `onClick`. The app is unusable by keyboard and largely opaque to a screen reader. `CONTEXT.md` §5.4 claims "Universal Accessibility"; that claim is not currently true.

2. **`--text-muted` fails AA contrast in dark mode at 2.61:1** (needs 4.5:1). It is the color of nearly every label, sublabel, timestamp, and hostname in the product, frequently at 9–11px. `CONTEXT.md` claims AAA in both themes — measured, dark mode has three tokens below AA and light mode has four.

3. **`MonitorModal.tsx:343` and `:424` hit a different API port than the rest of the app** (`8008` vs `App.tsx:19`'s `8000`). Test Connection and CSV bulk import talk to a host nothing else talks to. This is a functional bug, not a style issue.

4. **The database Engine Diagnostics panel opens into a dead state.** `dbActiveTab` initialises to `'info'` (`App.tsx:146`), but the tab bar only renders `slow_queries` and `tables` (`:1345`) and the content blocks only match those two (`:1366`, `:1417`). Opening any Postgres, Mongo or Redis monitor shows a tab bar with **no tab selected and nothing beneath it**. It reads as broken until the user happens to click. One-character fix.

5. **You cannot log out using a keyboard.** The avatar trigger is a `<div onClick>` (`App.tsx:695`), so the profile menu — and both User Preferences and Log Out inside it — has no keyboard path at all. See Part 5.

Beyond those: the WebSocket has no reconnect logic, and `fetchStatsAndIncidents()` fires on every inbound message — so a 50-monitor fleet generates ~100 HTTP requests per check cycle, and any network blip silently freezes the dashboard with no indication. For a monitoring tool, a dashboard that can't tell you it stopped monitoring is the worst available failure mode.

# Part 2 — React & performance (Vercel rules)

Ordered by impact.

### CRITICAL — `bundle-dynamic-imports`
`recharts` (~150 KB gzipped) is a static import at `App.tsx:2` and `ExecutiveDashboard.tsx:3`. Because `App` is one component, `MonitorModal`, `UserPreferencesModal`, `ExecutiveDashboard`, `PublicStatusPage` and all of recharts ship in the bundle that renders the **login screen**. Nobody logged out needs a charting library.

Fix: `React.lazy` the chart sections, all three modals, and `ExecutiveDashboard`; render the login form from a separate top-level branch.

### CRITICAL — `bundle-barrel-imports`
23 icons from the `lucide-react` barrel at `App.tsx:3–9`, 16 more at `UserPreferencesModal.tsx:2`, 9 at `ExecutiveDashboard.tsx:2`. Vite tree-shakes for production, but the dev server transforms the whole barrel every cold start.

Fix: `import Shield from 'lucide-react/dist/esm/icons/shield'`.

### CRITICAL — WebSocket has no reconnect and no error handling
`App.tsx:391–428` opens the socket once. There is no `onerror`, no `onclose`, no retry, and no connection-state indicator. A backend restart or a dropped Wi-Fi frame leaves the dashboard showing stale "up" statuses indefinitely, with nothing on screen to say so.

Fix: exponential-backoff reconnect, plus a visible connection pill in the navbar. For this product that's a correctness requirement, not a nicety.

### HIGH — request amplification
`App.tsx:420` calls `fetchStatsAndIncidents()` on **every** `target_update` message, and that helper fires 2 requests. 50 monitors on a 60s interval ≈ 100 HTTP requests per cycle, each triggering a full re-render.

Fix: debounce to ~1s, or have the backend include summary counts in the update frame.

### HIGH — `rerender-memo`
`App` is a single 2,085-line component holding ~30 `useState` values. Every WebSocket frame re-renders the navbar, the accent picker, every sidebar row and its 20–30 heartbeat bars, both charts, and all three modals.

Fix: extract `Navbar`, `MonitorList`, `MonitorRow` (memoized on `id`/`status`/`response_time_ms`), `KpiGrid`. Memoize `RadialGauge`.

### HIGH — `async-parallel` waterfall
`App.tsx:355–371`: heartbeats → await → metrics → await → db-engine-status. Three sequential round-trips every time a monitor is clicked. `Promise.all` them. (`:326–329` already does this correctly — good pattern, apply it here.)

### MEDIUM — `js-cache-storage`
`App.tsx:79, 88, 89, 95, 165` call `localStorage.getItem` in `useState(...)` **argument** position, so they execute on every render and the result is discarded after mount. `:106` already uses a lazy initializer correctly — apply the same shape to the other five.

### MEDIUM — `rendering-content-visibility` / virtualization
`App.tsx:823–926` (sidebar) and `:1657` (Infrastructure Overview) map unbounded arrays. Each sidebar row renders 20–30 heartbeat `<div>`s, so 50 monitors ≈ 1,500 extra nodes.

Fix: `content-visibility: auto` on rows now; `virtua` past ~100 monitors.

### MEDIUM — `js-combine-iterations`
```
App.tsx:1594/1596  - three full .filter() passes over filteredMonitors in adjacent expressions
App.tsx:1617       - filter + map + reduce where one loop suffices
App.tsx:1790-1793  - two complete filter passes inline in a button *label*, re-run on every keystroke
App.tsx:824-925    - the entire grouping pass (build groups, sort keys, recount actives) rebuilds on
                     every WebSocket message. Wrap in useMemo keyed on monitors/groupBy/searchTerm
```

### MEDIUM — `client-localstorage-schema`
Ten unversioned `snoomp_*` keys (`App.tsx:125–133`), plus a legacy-key migration already hiding at `:165` (`snoomp_group_by_tags`). Consolidate to one versioned `snoomp_prefs_v1` object.

### MEDIUM — `advanced-init-once`
`App.tsx:85` applies the accent in a `useEffect` after first paint → visible color flash. Move to an inline script in `index.html`, alongside the anti-FOUC block (which currently hardcodes dark, so light-theme users flash dark on every load).

### MEDIUM — CSV import robustness (`MonitorModal.tsx:71–153`, `:427–460`)
- `line.split(',')` — any quoted field or comma-containing password corrupts the row, which is then silently `continue`d with no report of skipped lines.
- `Promise.all` fires N unbounded concurrent POSTs; a 500-row CSV is 500 simultaneous requests.
- `:452` counts `r.ok`, but a single rejected fetch rejects the whole `Promise.all` and lands in `.catch`, discarding every partial result.

Fix: a real CSV parser, a concurrency limit (~5), `Promise.allSettled`, and a per-row result summary in the UI instead of `alert()`.

### LOW — `MonitorModal.tsx:20–55`

**Scope:** `frontend/src/**`, static source audit.
**Caveat:** the accesslint engine was not available in this session and no dev server was running, so this is source-derived. Contrast figures below are computed from the CSS tokens and are reliable; focus order, screen-reader announcement quality, and reflow behaviour need live verification.

## Summary

- **4 critical**, **6 serious**, **5 moderate** patterns after deduplication.

## Critical

### C1 — Custom controls are non-semantic and keyboard-inaccessible
- **WCAG:** 2.1.1 Keyboard (A), 4.1.2 Name/Role/Value (A)

Add `aria-expanded` to the group headers, accordion headers, and profile-menu trigger; `aria-pressed` to the tag chips and theme toggle.

### C2 — `--text-muted` fails AA in dark mode
- **WCAG:** 1.4.3 Contrast Minimum (AA)
- **Affected:** `dashboard.css:22` (token) — used ~120× across all files
- **Measured (dark):** `#4d5471` on `#0c0d12` = **2.61:1**; on `#181a24` = **2.33:1**. Needs 4.5:1.

# Part 4 — Design system: type and colour

The hues and the font choices are individually tasteful. The problems are structural: the type pairing does no work, the accent palette collides with the status palette, and three separate mechanisms that should build hierarchy are all too weak to do so.

## 4.1 Fonts — five families loaded, three used, two indistinguishable

```
index.html:11      - loads Plus Jakarta Sans + DM Sans + Noto Sans Mono
dashboard.css:7    - additionally @imports Outfit + JetBrains Mono. Neither is referenced by
                     any token. Render-blocking, zero usage — delete this line
dashboard.css:3    - header comment says "Geist", a fourth family that also isn't present
```

**The pairing is inert.** `--font-header` (DM Sans) and `--font-sans` (Plus Jakarta Sans) are both geometric-humanist sans with near-identical proportions, x-height and letterform construction. At the sizes actually used — 14px body, 18–32px headings — they are not perceptibly different. `--font-header` appears at 13 call sites and buys an extra font download for a distinction no reader can see. Hierarchy is currently carried entirely by size and weight, not by family.

Two defensible resolutions:
- **Cheaper:** drop DM Sans, use Plus Jakarta throughout, let weight and size carry hierarchy. Saves a request.
- **Better:** keep two families but pick a display face with real contrast against the body text. A condensed grotesque or a mono-derived display face suits an infrastructure console and would make the `--font-header` token earn its place.

`--font-mono: 'Noto Sans Mono'` for metrics is the right call, and it is correctly paired with `font-variant-numeric: tabular-nums`. Keep that.

## 4.2 Type scale — 20 sizes, 189 of 258 declarations inside a 4px band

| px | 9 | 9.5 | 10 | 10.5 | 11 | 11.5 | 12 | 13 | 14 | 15 | 16 | 17 | 18 | 20 | 22 | 24 | 28 | 32 | 36 | 48 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| uses | 9 | 1 | 44 | 1 | 51 | 1 | 52 | 42 | 5 | 12 | 1 | 2 | 12 | 8 | 2 | 3 | 5 | 2 | 3 | 1 |

This is a cluster, not a scale. The half-pixel values (9.5, 10.5, 11.5) confirm it grew ad hoc rather than being derived. Anything below 11px also fails practical legibility for the operational detail it carries.

**Weights are equally flat:** 400 × 3, 500 × 13, 600 × 64, 700 × 70, 800 × 17. 134 of 167 declarations are semibold or bold. When almost everything is emphasised, emphasis stops meaning anything.

**Fix:** collapse to six sizes (12 / 14 / 16 / 20 / 28 / 40), make 400 the actual default, reserve 600+ for genuine emphasis, and expose them as tokens so the next screen can't invent a 21st size.

## 4.3 Accent picker collides with the status palette

Measured as CIELAB ΔE. Below 10 reads as the same colour; below 5 is indistinguishable.

| Accent option | Collides with | ΔE | Verdict |
|---|---|---|---|
| Blue `#3b82f6` | `--color-maintenance` `#388bfd` | **4.3** | identical |
| Green `#34a853` | `--color-up` `#238636` | **13.1** | confusable |
| Cyan `#06b6d4` | `--color-maintenance` `#388bfd` | 57.3 | distinct ✓ |

Two of three accent choices make "brand / interactive" indistinguishable from "this host is healthy" or "this host is in maintenance" — in a product whose entire job is encoding state as colour. Cyan is the only safe option, which is an odd thing to be true of a palette whose default is Blue.

**Fix:** move the accent range off the status hues entirely — violet, magenta or amber-free warm neutral. Reserve green, red, amber and blue exclusively for state.

**Also:** the two accent lists disagree.
```
App.tsx:23-27                  - 3 options: "Blue", "Green", "Cyan"
UserPreferencesModal.tsx:77-82 - 4 options: "Azure Blue", "Emerald Green", "Cyan Tech",
                                 "Purple Ray" — different set, different names
```
Export one `ACCENT_OPTIONS` constant and import it in both places.

## 4.4 Chart series are hardcoded and semantically confusing

```
App.tsx:1239-1247, 1257-1267 - series colours are #faa81a, var(--accent), #7289da
App.tsx:1474-1483            - latency chart uses var(--accent)
```

- `#faa81a` (CPU) sits **ΔE 16** from `--color-warning` `#d29922` — close enough that a normal CPU line reads as an alert.
- `#7289da` (Disk) sits **ΔE 19.8** from `--color-maintenance` — another status-adjacent blue.
- With Blue accent selected, series 2 and 3 are both blue; series separation collapses.
- All three are hex literals, not tokens, so **none of them adapt to light mode.**

**Fix:** define `--chart-1/2/3` per theme, derived from hues the status palette doesn't use, and verify they remain distinct under every accent option.

## 4.5 Surfaces and borders are too weak to build hierarchy

Dark ladder, contrast between adjacent steps:

| step | ratio | ΔE |
|---|---|---|
| `--bg-void` → `--bg-primary` | 1.03 | 1.5 |
| `--bg-primary` → `--bg-secondary` | 1.05 | 3.3 |
| `--bg-secondary` → `--bg-elevated` | 1.07 | 4.2 |
| **void → elevated (total range)** | **1.15** | 9.0 |

Light ladder is tighter still — `--bg-secondary` → `--bg-elevated` is **1.03 / ΔE 1.1**, effectively one colour.

`--border: rgba(255,255,255,0.06)` composites over `--bg-secondary` to roughly `#1b1c23` — a **1.09:1** edge. WCAG 1.4.11 requires 3:1 for component boundaries, and perceptually it simply isn't there.

Both mechanisms that should separate a card from its background are near-zero simultaneously. That is why the design compensates with a full-viewport grain overlay (`dashboard.css:158`), glow shadows, and near-universal bold weights — decoration standing in for structure.

**Fix:** widen each surface step to ≈1.3× (e.g. `#0a0b10` / `#14161f` / `#1c1f2b` / `#262a38`), take `--border` to 12% white in dark and 12% black in light, then reassess whether the grain overlay is still earning its repaint cost.

# Part 6 — Aesthetic assessment

Requested explicitly: is the design good, and does it hold up in both themes? Direct answer, and it differs sharply by mode.

**Dark mode is not ugly. It is anonymous.**
**Light mode is not merely less attractive — it is structurally broken.**

## 6.1 Dark mode — competent, generic, and compensating

Dark mode reads as professional. The tinted blue-black canvas (rather than pure OLED black), the desaturated GitHub-style status palette, and the tabular-figure discipline are all correct decisions that many monitoring tools get wrong. Nobody will call it bad.

But it is the current default look for this category — near-black tinted background, single blue accent, hairline borders, glow shadows, grain texture. Nothing in it says *Snoomp* rather than any other dashboard shipped this year. Three specific reasons:

**The one distinctive idea is barely used.** The double-bezel enclosure is a real thesis — a hardware-panel metaphor for a tool that watches hardware. `CONTEXT.md` §5.4 lists it as a UI invariant. In practice it appears in **2 of 7 components** (`ExecutiveDashboard.tsx`, `UserPreferencesModal.tsx`) and nowhere in the dashboard, the sidebar, the monitor detail view, the status pages or either public surface. Everywhere else is a flat card with a 1px border. The idea that would give this product a face is used on two screens. Commit to it across the app or drop it — half-application reads as inconsistency, not as a system.

**Texture is standing in for structure.** With surfaces 1.03–1.07 apart and borders at 1.09:1, nothing actually separates a card from its background. The design compensates with a full-viewport `feTurbulence` grain overlay at 2.2% (`dashboard.css:173`), accent glow shadows, and near-universal bold weight (134 of 167 weight declarations at 600+). Those are three separate patches over one missing thing. Fix the surface ladder and most of that decoration can simply be deleted — the design will get quieter *and* clearer at the same time.

**The best element is hidden.** The heartbeat strip is the strongest thing in the interface: discrete time blocks, dense, scannable, and genuinely native to the subject — it looks like what monitoring *is*. It is currently 3px wide in a sidebar row and repeated as a tooltip-only detail view. That is the signature element. It should be the hero of the monitor detail page at full width with a real time axis, hover readouts, and outage bands — not a decorative micro-sparkline.

**Menu-level notes.** The navbar packs eight controls into 52px: three raw colour dots, three text buttons, a two-icon theme toggle, and an avatar. The colour dots are unlabelled 13px circles doing a settings job in a primary nav slot — they belong in the preferences dialog, which already has them. The sidebar itself is good: dense, scannable, correct information order. The Executive view, however, uses a different visual language from everything else — 32px headings against 24px elsewhere, double-bezel against flat cards, 24px gaps against 16px — so it reads as a different product bolted on.

## 6.2 Light mode — this one has real problems

Light mode is not a theme; it is a token swap that leaves a large amount of dark-mode-only styling in place. Specifics:

**There is no elevation at all.** The top three light surfaces are `#F4F6F8` / `#F9FAFB` / `#FCFDFD` — separated by **1.04:1** and **1.03:1**. Effectively one white. In dark mode shadows partly rescue this; in light mode `--shadow-sm` is `0 1px 2px rgba(0,0,0,0.03)` — **3% black**, which is invisible. Combined with `--border` at 6% black (≈1.05:1), a card in light mode has no background difference, no border you can see, and no shadow. It does not read as a surface.

**46 hardcoded white-alpha backgrounds disappear.** `rgba(255,255,255,0.02–0.05)` is used 14× in `App.tsx`, 7× in `MonitorModal.tsx`, 1× in `PublicStatusPage.tsx` and 24× in `dashboard.css`. Every one is white-on-white in light mode. This includes the entire database stat-card row (`App.tsx:1354–1376`), the diagnostics tab bar (`:1397`), and the report summary cards (`:2013–2025`) — panels that are visible in dark mode and simply vanish in light.

**Chart gridlines are invisible.** `CartesianGrid stroke="rgba(255,255,255,0.03)"` at `App.tsx:1314` and `:1579`. White gridlines on a white canvas, in both charts.

**Light `--chart-2` is the weakest series at 3.4:1** on the light canvas — it clears the 3:1 graphics threshold but only just, and it sits next to two series at 5.26 and 4.24. Darken it to roughly `#0e7490`.

**Dark-mode idioms carry over.** `--shadow-glow: 0 0 15px var(--accent-glow)` is a neon effect; on white it reads as a smudge. The grain overlay uses `mix-blend-mode: overlay` at 2.2%, which does almost nothing over near-white — so light mode loses the texture that dark mode leans on, making the flatness worse rather than better. And `App.tsx:1658` hardcodes `color: '#fff'` on the status banner heading, which is white text on a 10%-tinted light background — near-invisible.

**Verdict:** if a user switches to light mode today they will see a flat white page with floating unbordered text, missing panels, and gridless charts. This is worth prioritising above most of the remaining accessibility work, because it affects every sighted user who prefers light themes — likely a large share of a daytime NOC audience.

## 6.3 What I would actually do

Ranked by visible improvement per hour of work:
